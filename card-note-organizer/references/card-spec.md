# 卡片笔记规范

## 卡片标准结构

每张卡片必须包含以下部分（关键图示仅在原文有图时出现），严格使用以下 Markdown 格式：

```markdown
---

**标题不超十字**
### 🏷️ 标签

`#书名/章节名` `#内容标签1` `#内容标签2` `#内容标签3` `#核心概念/术语`

### 💬 一句话总结

用一句话（不超过 60 字）概括这条笔记的核心信息。

### 📌 核心要点

忠实保留输入材料中最重要的观点、结论、清单、因果关系。
这一层的职责是"原文说了什么重要的东西"——允许适度精简和结构化，但不歪曲、不丢失关键内容。
呈现方式灵活选择（列表/表格/段落），重要的是结构清晰、逻辑明确、易理解。

### 💡 洞见

基于上方核心要点，提炼出原文没有直接说出的上位判断、关联、启发或延伸思考。
这一层的职责是"我从中看到了什么额外的东西"——观点必须清楚，不需要固定结构，依据内容自由提炼。
如果某条笔记确实没有值得额外提炼的洞见，可以不写此区段。

### 🖼️ 关键图示

（仅当原文存在核心图示时出现；按出现顺序保留所有核心图示，可附简短 caption）

![[图1 文件名.png]]
*图 1：caption 说明*

![](https://example.com/diagram.png)
*图 2：caption 说明*

### 📎 来源

- **出处**：具体来源名称、作者、链接等
- **日期**：YYYY-MM-DD（如果有）
```

## 各字段详细规范

### 标题

- 不超过 10 个汉字
- 用名词短语或短句概括核心主题
- 避免空泛标题，如「读书笔记」「一些想法」
- 标题应便于在 Obsidian、Reminds 或文件中快速检索
- **鼓励使用结构化命名**增强记忆度：公式型（"经验是阅读×经历×思考"）、隐喻型（"推动力的三个支点"）、并列型（"三种能力三条路"）优于平铺直叙

### 标签

标签分为三类：**出处标签**、**内容标签** 和 **概念标签**，**三类共占一行**，不单独设置二级标题。

- 出处标签：1-2 个，用来标识内容来源；默认 1 个，只有来源层级复杂或需要保留两个独立来源线索时才用 2 个。
- 内容标签：2-5 个，由笔记参考的原文和内容总结提炼而成，用来表达主题、概念、方法、行动或领域。
- 概念标签：数量不限，标注笔记内容涉及的**核心概念、术语、理论、模型**等。判断标准：该概念是否对这条笔记的论点构成关键支撑或直接关联？是 → 加入；仅顺带提及、作为背景或举例出现 → 不加。例如本条笔记以 Miller's Law 为核心依据则加 `#Miller's Law`，但如果某条笔记只是顺嘴举例"就像 Miller's Law 那样"则不加。
- **三类标签混排在同一行**，不区分先后顺序，不设「概念标签」子标题。
- 总量：出处 + 内容标签通常 3-6 个，复杂笔记最多 7 个；概念标签不计入此上限，但必须每个都与笔记核心强相关，避免为了凑数制造弱标签。
- 层级从宽到窄：从领域大类逐步细化到具体概念。
- 兼顾检索与关联：既要方便日后搜索，也要能串联相关笔记。
- 使用中文标签，简洁准确，2-6 字为宜；出处标签可因书名/章节名适当更长；概念标签可使用原文术语（中文或英文均可，如 `#Millers-Law`、`#心流`）。
- **特殊字符处理**：标签中不能出现会截断解析的字符（撇号 `'`、空格、引号等）。遇到时统一处理：去掉特殊字符，用连字符 `-` 连接多词。例如：`Miller's Law` → `#Millers-Law`，`Don't Repeat Yourself` → `#Dont-Repeat-Yourself`，`7±2` → 不写入标签内，在正文中保留即可。
- 出处标签可使用 `/` 分割多级层级；例如来自某本书某章节的划线，使用 `#书名/章节名`，来自网页可用 `#网站名/栏目名`。

### 一句话总结

- 控制在 60 字以内，简洁准确
- 包含「主题 + 核心观点/发现」，而非仅仅描述主题
- 即使脱离上下文也能独立理解
- 使用肯定句式，避免模糊表达
- **禁止在总结末尾标注字数**（如"（55字）"），字数限制是内部规范，不对读者展示

### 核心要点

「核心要点」的职责是**忠实传达输入材料中最重要的观点、结论、清单、因果关系**——"原文说了什么重要的东西"。

**规则：**

- **不需要保留原文的表述格式**——应主动整理出更清晰的结构来呈现原文意思。忠实的对象是原文的**含义和关键信息**，不是原文的句式或排版。
- 呈现方式灵活选择（列表/表格/段落），核心原则是**结构清晰、逻辑明确、易理解**。
- 原文中的关键清单、对比、因果链等重要**信息**必须保留，但可以用不同于原文的形式重新组织。
- 可以用加粗小标题分组呈现多个要点群（如"效果""适用场景""注意事项"等）。

**重组策略选择指引：**

根据原文的底层逻辑关系，选择最适合的呈现方式：

| 原文特征 | 推荐呈现方式 | 典型场景 |
|----------|-------------|----------|
| 多个并列概念容易混淆 | 表格（含「关键区分」列） | 三个维度各有易混点：阅读≠看书、年限≠经验 |
| 大量条目有隐藏主题 | 按主题分组 + 编号标题 | 12 条规则→重组为 5 类 |
| 明确的递进/因果/步骤 | 有序列表 + 加粗标签 | "先…再…然后…"的逻辑链 |
| 对比/二分结构 | 嵌套列表或对比段落 | "新手可以 X，但成熟的必须 Y" |
| 单一论断 + 展开说明 | 自然段落 + 加粗关键判断 | 一句核心观点 + 补充解释 |

选择原则：
- 先识别原文的逻辑关系（并列？递进？对比？分类？），再选格式
- 如果一张卡内同时存在多种关系，可混合使用（如先分组标题，组内用表格）
- 不要为了"看起来丰富"而强行用表格/列表——如果原文本身就是一个清晰的自然段，保持段落即可

### 洞见

「洞见」的职责是**基于核心要点，提炼出原文没有直接说出的上位判断、关联、启发或延伸思考**——"我从中看到了什么额外的东西"。

**规则：**

- 观点必须清楚，但**格式必须结构化、易读**。单观点超过3句话时拆分为层次段落或要点；多观点用加粗小标题分组呈现。同「核心要点」的格式手段（表格/有序列表/无序列表/加粗标签/引用块）均可使用，原则是**易读优先**。
- 不要复述核心要点中已经写过的内容，这一层只写"额外的判断"。
- 如果某条笔记确实没有值得额外提炼的洞见，**可以不写此区段**。
- 好的洞见通常是：上位概念归纳、跨领域类比、因果归因、方法论命名、实操启发等。
- **最佳模式**：揭示多条表面规则背后的**统一原理或运作模型**——例如将 12 条产品原则归结为"减少用户成本"这一条主线，或识别出"木桶效应"这一隐藏模型。
- **结构化指引**：当洞见涉及多个维度时，按维度拆分（如「上位概念」「因果归因」「跨领域类比」），用加粗短语标记每个维度。避免把所有判断挤进一段长文字。

### 核心要点与洞见的关系

两个区段各司其职，不能混淆：

| | 核心要点 📌 | 洞见 💡 |
|---|---|---|
| 职责 | 忠实传达原文核心内容 | 提炼额外判断 |
| 标准 | 原文说了什么重要的 | 我从中看到了什么 |
| 允许 | 重新组织结构、精简、重组 | 自由提炼、跨领域关联 |
| 禁止 | 歪曲或丢失关键信息 | 复述核心要点已有内容 |
| 可选性 | 必写 | 无值得提炼时可不写 |

### 格式与排版通用规则

以下规则适用于「核心要点」和「洞见」两个区段：

1. **呈现方式灵活选择**：基于内容特点选择最易读、易理解的呈现方式。核心原则是**易读性和易理解性**，不拘泥于固定形式。具体指引：
   - **表格**：适合各点之间是**并列对比**关系（如 A vs B vs C、多维度比较）。当概念容易与近义词或常见误解混淆时，主动增加「关键区分」列（如"阅读≠看书""工作年限≠经验"），帮助读者建立精准认知边界。
   - **自然段落**：适合各点之间是**递进/因果链**关系（从"是什么"→"为什么"→"所以"逐层深入）；通过段落间的逻辑连接词体现推进，不要用无序 bullet 表达递进。
   - **编号列表**：适合有明确**先后顺序或步骤**的内容。
   - **无序列表（`-`）**：仅用于各点**地位等同、真正并列**的情况；注意同级 bullet 天然传达并列关系，不要用它表达递进或因果。
   - **引用块**：适合收束总结、补充金句或底层逻辑。

2. **善用格式标记与标点符号**：格式标记是提升可读性的重要手段，不要写成纯平文本。各标记的适用场景（参考 Wikipedia Manual of Style、MDN 文档、Chicago Manual of Style）：

   - **粗体** `<b>` / `**...**`：标记**重要性**——核心概念首次出现、关键判断、步骤名称、定义中的被定义项。读者扫读时第一眼应该看到的内容。
     - ✅ 适用：核心概念名词、关键结论句、步骤标题
     - ❌ 不适用：大段强调（粗体超过一句则失去强调效果）、单纯为了"好看"

   - *斜体* `<i>` / `*...*`：标记**辅助信息**——地位低于正文主体，属于"可跳过但有助理解"的补充层。语义上表示"这段话是旁白/注释/例证，不是主线论述"。
     - ✅ 适用：① 举例说明（*"搭载最新技术的电动车"是套话*）；② 对前文的补充注释/旁白；③ 引述中的非核心原文片段；④ 外来术语首次出现时的原文标注；⑤ 语气/情绪标注（*本质上这就是认知工程*）
     - ❌ 不适用：整段斜体（丧失区分度）、已用引用块包裹的内容内部再斜体（冗余）
     - 📖 来源：Wikipedia MOS 规定斜体用于 emphasis（强调对比）、titles（作品名）、words-as-words（讨论词语本身）、foreign terms（外语术语）

   - ==高亮== `<mark>`：标记**相关性**——整条笔记中最需要读者注意的 1-2 处核心数字或结论。语义是"这个信息在当前上下文中特别值得注意"，类似用荧光笔标记。
     - ✅ 适用：关键数字（*<mark>7±2</mark>*）、一句话核心结论、需要特别记忆的判断标准
     - ❌ 不适用：超过 2 处（滥用则无效）、整句高亮（应精确到关键词/短语）
     - 📖 来源：MDN 定义 `<mark>` 为"因在上下文中具有相关性而被标记的文本"，与 `<strong>`（重要性）区分

   - `>` 引用块 `<blockquote>`：标记**引用或区隔内容**——需要与主体段落做视觉分离的补充性内容。语义是"这段话来自别处"或"这段话是对主体的补充/收束"。
     - ✅ 适用：① 直接引用原文定义/金句；② 底层逻辑收束（对前文的抽象总结）；③ 变通方案/注意事项；④ 操作提示/边界条件
     - ❌ 不适用：正文核心论述（不应把主要观点放进引用块）、仅为缩进美观（语义滥用）
     - 📖 来源：MDN/WHATWG 规定 `<blockquote>` 语义为"引自其他来源的内容"；在笔记场景中扩展为"与主体做视觉区隔的补充"

   - 列表：根据内容逻辑关系选择类型。
     - **有序列表** `<ol>`：有明确先后顺序或步骤流程的内容
     - **无序列表** `<ul>`：各点地位等同、真正并列的内容
     - **嵌套列表**：表达从属/包含关系，但避免超过 2 层嵌套（过深则改用表格或段落）
     - ❌ 不适用：用无序列表表达递进/因果（同级 bullet 天然传达并列）

   - 标点符号：灵活选用「」、""、【】、() 等辅助强调，根据语境和可读性自行判断。
   
   写入 Reminds 时，必须参照 reminds-writer skill 中定义的 HTML 渲染规范，善用 `<b>`、`<i>`、`<blockquote>`、`<mark>`、`<table>`、`<hr>` 等标签实现视觉层级区分。

3. **洞见区的额外要求**：
   - 观点必须清楚——写完后自问"这段话原文有没有直接说过？"如果有，说明还在复述，必须重新抽象。
   - 好的提炼应产出：上位概念、因果归因、跨领域类比、方法论命名等原文没有直接给出的东西。
   - 不需要固定数量的支撑点，也不需要金字塔结构——自由发挥，但观点必须明确。
   - **长段落必须结构化**：用加粗短语标记维度标签（如「上位概念」「因果归因」「类比关联」等），分拆为短段或 bullet 呈现。多观点时每条一句话讲清一个判断，避免文字墙。

4. **术语处理原则**：读者不认识术语也能完全理解句意。具体方式灵活选择：有检索/关联价值的术语保留并用直白中文解释在先（术语作标注）；无特别价值的术语直接省略只写含义；抽象概念可辅以类比。**禁止术语当主语、括号里塞一个不对等的翻译词就算交代。**

**反面模式（必须避免）：**

- 在洞见区复述核心要点已有的内容，造成重复。
- 把原文要点变成多级嵌套清单，但没有提炼出额外判断。
- 大量使用"原文指出/原文提到/作者认为"，导致文本停留在转述层。
- **核心要点区丢失原文重要内容**：为了"精简"而删掉原文关键清单、对比或结论。
- **不考虑易读性**：机械使用某种固定格式而不考虑内容特点，导致可读性差。
- **用无序 bullet 表达递进/因果**：同级 bullet 天然传达并列关系，用它来写"是什么→为什么→所以"会让读者误以为各点独立等价。
- **术语堆砌不解释**：用专业术语当主语，括号里只放一个不对等的翻译词（如"Pop-out（并行）"），读者仍然不知道这个概念到底是什么意思。
- **格式单一、不做视觉区隔**：所有内容（主体判断、补充说明、变通方案、注意事项）全部挤在同级段落或 bullet 中，不利用引用块、高亮、斜体等格式手段区分信息层级。

**示例（新结构：核心要点 + 洞见）：**

```markdown
**简报要写明主语**
### 🏷️ 标签
`#你的简报就是比AI强` `#简报写作` `#信息表达` `#认知负担`

### 💬 一句话总结
简报中每句话都应有明确主语，这既降低观众认知成本，又能通过主语切换改变信息的感知角度。

### 📌 核心要点
**明确主语带来五个正面效果：**
1. 减轻认知负担
2. 提高信息的一致性和明确性
3. 提高记忆的扎根
4. 防止误会
5. 提升兴趣

**不同主语起不同修辞作用：**

| 主语 | 适用场景 |
|------|---------|
| 我 | 强调个人的责任或参与 |
| 自家公司、公司 | 强调组织利益或效率 |
| 无（省略主语） | 强调客观事实或逻辑性观点 |

**简洁不等于省略主语：** 减少文字数量的简洁表现是简报的制作原则，但如果连必要的主语都省略，导致意思不明确，就是本末倒置。巧妙使用主语，可以预防与观众之间的理解落差。

### 💡 洞见
主语选择是一种隐性的"视角控制"。多数人写简报时省略主语只是出于习惯或追求简洁，但实际上每次省略都是在让观众自己去猜"这是谁的事"——猜对了没感觉，猜错了就产生理解落差。而主动选择主语（我/公司/省略），其实是在决定让观众以什么立场接收信息，这是一个被低估的修辞杠杆。

### 📎 来源
- **出处**：《你的简报就是比AI强》
```

**其他要求：**

- 忠实原意：不歪曲原始笔记的内容。
- 核心要点区必须保留原文的关键内容，不能为了"精简"而丢失。
- 洞见区以提炼额外判断为主，不重复核心要点已有内容。
- 区分事实与观点：明确标注哪些是作者观点、哪些是客观事实。
- 必要时在结尾追加「关联笔记」一句，提示与其他卡片的连接。

### 关键图示（图片处理总则）

**总则：原文中出现的任何图片都必须被处理，不能默默丢掉。**

#### 1. 识别

解析输入时主动扫描三种语法，得到图片清单：

- 标准 Markdown：`![alt](path or url)`
- Obsidian wiki link：`![[file.png]]`、`![[file.png|caption]]`
- HTML：`<img src="..." />`

#### 2. 取舍

每张图按以下标准判定：

| 类别 | 处理 | 例子 |
|------|------|------|
| **核心图示** | 必须保留，进「关键图示」区段 | 流程图、框架图、概念图、对比图、原理示意图、数据图表 |
| **装饰/封面图** | 可丢弃，但应在末尾留一行说明「原文有 X 张装饰图未保留」 | 章节封面、纯氛围插图、与内容弱相关的配图 |

判别原则：**这张图丢了之后，对核心论点的理解是否会有损失？** 有损失 → 核心图示。

#### 3. 写入

不同输出目标的写入方式：

| 输出目标 | 图片写法 |
|---------|---------|
| **本地 md / Obsidian** | 保留原 wiki link `![[file.png]]` 或标准 `![](relative/path.png)`，便于在 vault 内自动渲染 |
| **Reminds（HTML）** | **必须直接嵌入 HTML，不能仅留路径文字**：① 远程图片用 `<img src="https://..." alt="..." />`；② 本地图片读取文件并转为 `data:image/<ext>;base64,<...>` 内联到 `<img src>` 中；③ Obsidian wiki link 必须先解析到真实文件，再走 base64 路径 |
| **CSV / JSON** | 在 `images` 字段记录原始引用列表（不展开 base64） |

#### 4. Caption

- 优先使用原文给出的 alt / 图注（`![alt](...)` 中的 alt、`![[file.png|caption]]` 中的 caption、HTML 中的 figcaption）。
- 原文没有 caption 时，根据上下文用一句简短中文给出（如「图：商业模式画布九大模块」）。

#### 5. 解析失败兜底

Obsidian wiki link 在以下路径未能解析到真实文件时（按优先级）：

1. md 同目录下的 `attachments/`
2. md 同目录下的 `assets/`
3. vault 根目录递归搜索

仍然失败时，**保留原 wiki link** 并在卡片中加一行斜体说明：「*图片解析失败，请见原笔记 X*」，同时在最终回复中告诉用户。

#### 6. Reminds 图片大小

- 单张图片 base64 后建议 ≤ 1MB（防止单条 fleeting 体积过大）。
- 如果原图明显过大（>2MB），优先用远程链接；若必须本地内联，可适度压缩或请求用户确认。

### 来源

- 出处：书名/文章标题/URL/人名等
- 日期：尽可能标注
- 如果用户未提供来源信息，使用「用户提供，未注明出处」并提醒用户补充
- 不需要标注「类型」字段

### 关联笔记

在「来源」之后，基于 Reminds 中已有笔记的标题和标签，列出与当前卡片**强相关**的已有笔记链接。

**规则：**

- 格式：`@笔记标题`，每条一行
- 关联判断依据：标签强相关（不要求标签完全一致，语义强相关即可）、同一主题域、互为补充或递进关系
- 数量不限制，但只链接**强相关**的笔记，宁缺毋滥
- 一次整理多张卡片时，新卡片之间也要互相链接
- 执行流程：写入新卡片前，调用 `mcp__reminds-mcp__search_notes` 搜索现有笔记（基于当前卡片的标签和主题关键词），从搜索结果中筛选强相关条目

**示例：**

```markdown
### 🔗 关联笔记
- @推动决策落地九种影响力
- @天下皆为利来往
- @推动力的三个支点
```

## Reminds 写入格式

当输出目标是 Reminds 时，必须遵循以下规则：

1. **Markdown 是唯一信息源**：HTML 必须从已确认的 Markdown 卡片忠实转换而来，不得独立撰写。转换时逐条核对——文字内容逐字对应、emoji 不遗漏、格式标记（`**加粗**`→`<b>`、`*斜体*`→`<i>`、`==高亮==`→`<mark>`）全部带到 HTML。禁止「Markdown 有但 HTML 漏掉」的任何单项。
2. 保留每个部分的标题，不要省略「标签」「一句话总结」「核心要点」「洞见」「关键图示」「来源」「关联笔记」标题（关键图示仅在原文有图时出现；洞见在无值得提炼时可不写；关联笔记在有强相关已有笔记时出现）。
3. 每个部分的标题前固定使用对应 emoji：`### 🏷️ 标签`、`### 💬 一句话总结`、`### 📌 核心要点`、`### 💡 洞见`、`### 🖼️ 关键图示`、`### 📎 来源`、`### 🔗 关联笔记`。
4. 标题与标签之间**不使用分割线**，标签紧跟标题下方；其余各部分之间使用 Markdown 分割线 `---` 分隔；转换为 HTML 时使用 `<hr>`。
5. 按 Markdown 层级组织内容；转换为 HTML 时用 `<strong>`、`<em>`、`<blockquote>`、`<mark>` 等区分主次。
6. 标签部分包含 1-2 个出处标签（必要时才用两个）和 2-5 个内容标签；出处标签必要时使用 `/` 分割多级标签，例如 `#芒格之道/2022年每日期刊股东会讲话`。
7. 核心要点区保留原文关键内容，不能为了精简而丢失；洞见区只写额外判断，不重复核心要点。
8. **图片必须直接嵌入 HTML**：远程图片用 `<img src="https://..." />`；本地图片读取文件并转为 `data:image/<ext>;base64,...` 内联；Reminds 内部协议图片（`reminds://img/...`）直接用 `<img src="reminds://..." />`；禁止仅留路径文字代替图片；caption 用 `<figcaption>` 或紧跟图片的 `<p><em>...</em></p>`。

推荐 Reminds HTML 结构：

```html
<p><b>标题不超十字</b></p>
<h3>🏷️ 标签</h3>
<p><code>#书名/章节名</code> <code>#内容标签1</code> <code>#内容标签2</code></p>
<hr>
<h3>💬 一句话总结</h3>
<p><strong>一句话总结内容</strong></p>
<hr>
<h3>📌 核心要点</h3>
<!-- 灵活选择列表/表格/段落，保留原文关键内容 -->
<p><b>要点分组标题：</b></p>
<ol>
<li>要点 1</li>
<li>要点 2</li>
</ol>
<table>
<tr><th>维度</th><th>内容</th></tr>
<tr><td>...</td><td>...</td></tr>
</table>
<hr>
<h3>💡 洞见</h3>
<p>基于核心要点提炼的额外判断、上位概念、跨领域关联等。观点清楚，自由发挥。</p>
<hr>
<h3>🖼️ 关键图示</h3>
<figure>
  <img src="reminds://img/..." alt="图示说明" />
  <figcaption>图：caption 说明</figcaption>
</figure>
<hr>
<h3>📎 来源</h3>
<ul><li><strong>出处：</strong>《书名》</li><li><strong>日期：</strong>2026-05-31</li></ul>
<hr>
<h3>🔗 关联笔记</h3>
<ul>
<li>@已有笔记标题1</li>
<li>@已有笔记标题2</li>
</ul>
```

### Reminds HTML 渲染支持参考

以下是 Reminds 渲染端实际支持的 HTML 标签和转换规则（来源：reminds-writer skill 验证）：

#### 支持的标签

| 标签 | 用途 | 示例 |
|------|------|------|
| `<h1>` `<h2>` `<h3>` | 标题层级 | `<h1>主标题</h1>` |
| `<p>` | 段落 | `<p>正文内容</p>` |
| `<b>` / `<strong>` | 粗体强调 | `<b>关键概念</b>` |
| `<i>` / `<em>` | 斜体/补充说明 | `<i>注释内容</i>` |
| `<blockquote>` | 引用/定义 | `<blockquote>引用原文</blockquote>` |
| `<ul>` + `<li>` | 无序列表 | `<ul><li>项目</li></ul>` |
| `<ol>` + `<li>` | 有序列表 | `<ol><li>步骤1</li></ol>` |
| 嵌套 `<ul>` | 多级列表 | `<ul><li>父<ul><li>子</li></ul></li></ul>` |
| `<table>` | 表格 | 含 `<tr>` `<th>` `<td>` |
| `<hr>` | 分割线 | `<hr>` |
| `<br>` | 换行 | `<br>` |
| `<a href="url">` | 链接 | `<a href="https://...">文本</a>` |
| `<mark>` | 高亮（黄色背景） | `<mark>高亮文本</mark>` |
| `<img src="...">` | 图片 | `<img src="reminds://img/..." />` |
| `<figure>` + `<figcaption>` | 图片 + 标注 | 见上方 HTML 结构示例 |
| `<code>` | 行内代码样式 | `<code>#标签名</code>` |

#### 不支持 / 需注意

- `==` Markdown 高亮语法（不渲染，用 `<mark>` 替代）
- 原生 Markdown 语法（必须转换为 HTML）
- `<pre>` 代码块（可能不渲染等宽字体）
- `<br/>` 自闭合写法（用 `<br>` 即可）

#### Markdown → HTML 转换规则

| Markdown 元素 | 转换为 HTML |
|---------------|-------------|
| `# 标题` | `<h1>标题</h1>` |
| `## 标题` | `<h2>标题</h2>` |
| `### 标题` | `<h3>标题</h3>` |
| `**粗体**` | `<b>粗体</b>` |
| `*斜体*` | `<i>斜体</i>` |
| `> 引用` | `<blockquote>引用</blockquote>` |
| `- 列表项` | `<ul><li>列表项</li></ul>` |
| `1. 有序` | `<ol><li>有序</li></ol>` |
| 表格 `| a | b |` | `<table><tr><th>a</th><th>b</th></tr>...</table>` |
| `---` 分割线 | `<hr>` |
| `==高亮==` | `<mark>高亮</mark>` |
| `` `代码` `` | `<code>代码</code>` |

#### 格式最佳实践

1. 段落之间用 `<p>` 包裹，不要裸文本
2. 表格完整使用 `<table><tr><th>/<td>` 结构，确保有表头行
3. 嵌套列表用 `<ul>` 嵌套在 `<li>` 内部表达层级
4. 分割线 `<hr>` 用于分隔不同章节/区段
5. 核心要点区内不同要点群之间用 `<br>` 空行分隔（不用 `<hr>`）

## 批量处理格式

- 用 `---`（水平线）作为卡片之间的分隔符
- 为每张卡片编号（如 `## 卡片 1`、`## 卡片 2`）
- 在全部卡片末尾生成一个「标签索引」，列出所有标签及其对应的卡片编号

## 质量自检清单

在输出每张卡片前，确认：

- [ ] 标题不超过 10 个汉字，且能准确概括主题
- [ ] 出处标签 1-2 个；默认 1 个，必要时才用 2 个，且可用 `/` 表达来源层级
- [ ] 内容标签 2-5 个，来自原文和内容总结的主题/概念/方法提炼，具备检索价值
- [ ] 概念标签已标注笔记核心涉及的术语/理论/模型；每个都与笔记论点强相关，非顺带提及
- [ ] 一句话总结不超过 60 字，且包含实质信息
- [ ] 核心要点区保留了原文所有关键内容（清单、对比、因果链等），未因精简而丢失
- [ ] 核心要点区结构清晰、逻辑明确，呈现方式（列表/表格/段落）与内容匹配
- [ ] 洞见区（如有）只写额外判断，未重复核心要点已有内容
- [ ] 洞见区观点清楚，不是对原文的改写或复述
- [ ] 没有机械滥用"原文指出/原文提到/作者认为"
- [ ] 默认只使用一级 bullet，没有无必要的多级列表
- [ ] 原文若有图片，已识别并按「核心图示 vs 装饰图」做了取舍
- [ ] 所有核心图示已写入「🖼️ 关键图示」区段（写入 Reminds 时必须直接嵌入 `<img>`，不能只留路径文字）
- [ ] 来源信息完整（至少包含出处；日期尽量标注）
- [ ] 关联笔记区（如有）只链接强相关笔记，格式为 `@笔记标题`
- [ ] 整体格式美观、易于阅读
